# 删除块回收与长期离线设备重建方案

> 修订说明（2026-11-04）：本稿统一采用 90 天的结论已撤回。官方实践调研与只读容量实测后的建议为同步回收窗口默认 30 天、15 天可配置，历史保留独立设置；应按实际可用同步边界判定重建。以[行业调研与修订结论](mobile-retention-industry-review-20261104.md)为准。下文保留为原始设计讨论，其中固定 90 天的期限、首次观察期及纯按离线天数重建的表述不再作为实施要求。

状态：设计提案，尚未实现或执行回收。日期：2026-11-04。适用项目：Metahub Core 与桌面、Web、iOS、Android 客户端。代码基线：`feat/mobile`，`331e58b` 及当前同步解析修复。

建议采用 **90 天的删除保留期与设备同步兼容期**。永久删除必须通过完整的新同步协议完成：先保护本地编辑，再建立不可回退的新同步代际，最后回收旧数据。首版只回收 `doc_blocks` 的已删除块；同时修复编辑时不断生成新块 ID 的来源。

## 1 为什么选 90 天

2026-11-04 16:08（Asia/Shanghai）只读统计本机已同步数据库：

| 删除年龄 | 已删除块数 |
| --- | ---: |
| 不足 7 天 | 137 |
| 7 至 30 天 | 431 |
| 30 至 60 天 | 447 |
| 60 至 90 天 | 1,560 |
| 90 至 180 天 | 4,858 |
| 合计 | 7,433 |

候选计算同时要求最后一次块字段写入也超过阈值：

| 阈值 | 按年龄可成为候选的块 | 占已删除块比例 | 本次选择 |
| --- | ---: | ---: | --- |
| 30 天 | 6,865 | 92.4% | 兼容期过短 |
| 60 天 | 6,418 | 86.3% | 可节省更多，但没有离线设备分布证明应缩短到这里 |
| 90 天 | 4,858 | 65.4% | 默认采用 |

这里的年龄取已删除行对应的最新删除 HLC 和全部字段最大 HLC；它用于容量分析，**不是生产回收的安全凭据**。统计查询只输出聚合结果，无正文、设备标识、密钥或桶配置。数据持续变化，早先统计的 7,410 个已删除块与本次 7,433 个属于不同时点。

同日此前的云端快照样本为 1,410,405 bytes，约 1.41 MB（1.35 MiB）；更早样本解密解压后约 9.85 MB。此前快照有 44,858 条字段级变更，44,858 个唯一寄存器，其中 `doc_blocks` 42,221 条，约 94%；7,410 个删除块占 31,730 个字段，约 71%。这是“字段赢家仍包含已删除实体”，不等于快照重复保存全部历史。

90 天已经覆盖约三分之二的删除块，且与现有 `mh compact` 默认 90 天一致。30 天相对 90 天多覆盖 2,007 个块，但当前传输体积尚不足以支持牺牲两个月兼容期。iOS 本次同步失败已定位为解析调度与超时预算问题，应独立修复，不能把成功同步建立在删除数据上。

**不能据块数量推算压缩后的节省比例。** 重复文本压缩率不同；正式 dry-run 必须输出原始字节、压缩加密字节、字段数、峰值内存与解析耗时。当前也没有可信的设备同步确认记录，不能声称 90 天覆盖了实际设备离线分布。

## 2 对用户的明确承诺

| 事项 | 默认边界与行为 |
| --- | --- |
| 删除块保留 | 删除被回收协调节点确认后至少 90 天；后续有效修改、恢复或不确定性会延后回收 |
| 设备增量同步资格 | 自最近一次合格的持久化同步确认起 90 天；打开应用、心跳、上传一个操作均不能续期 |
| 超期设备 | 本地仍可编辑；再次联网时先保存本地编辑，重新下载当前状态，再恢复编辑；不能继续上传旧操作流 |
| 历史 | 对已收集且有完整覆盖证明的历史保留最近 90 天及窗口起点基线；缺失区间明确显示，不虚构历史 |
| 回收保护期 | 新代际提交后旧数据再保留至少 7 天；正常同步立即停止读取这些旧数据 |
| 未处理的本地编辑 | 不随 90 天或 7 天规则自动删除，直到用户确认恢复或明确丢弃 |
| 当前有效内容 | 不因创建时间久、长期没打开而回收 |

90 天是最短保护期和兼容窗口，不是承诺第 91 天一定释放磁盘。正常最早物理清除时间是确认删除后 90 天，再加提交后 7 天保护期；设备屏障、历史依赖或故障可能继续推迟。

“彻底删除”指受管理的在线副本与云端同步对象完成清除；无法远程擦除长期离线的设备、用户导出的备份或外部备份。旧设备再接入后按新代际重建。恢复包仍由用户控制，不能对它承诺自动清除。

首版不提供任意缩短到 0 天的开关。现有 `compact --keep` 仍只影响本地历史压缩，不能改变工作区的设备资格、代际和永久回收规则。

## 3 现有机制与必须补齐的能力

| 当前实现 | 对方案的约束 |
| --- | --- |
| `documents.ts` 用正文文本 LCS 匹配块；改字通常删除旧 ID 并创建新 ID | 优先减少无意义的块身份更替 |
| `storage.ts` 快照保留每个 `(dataset,row_id,col)` 的赢家 | 普通快照合并不会删除 tombstone 或其余旧字段 |
| `compact.ts` 只删除同寄存器被覆盖的旧写入 | 当前安全性依赖 tombstone 赢家仍存在，不可直接扩展 SQL 删除它 |
| `.vc` 存每个作者的最大 HLC | 不能证明中间没有缺口，不能当作可回收水位 |
| `publisher-lease.ts` 是允许短暂双发布的尽力选举 | 不可用作永久删除的独占权 |
| 设备列表含作者活动、心跳和本地 peer 状态 | 不等价于全局持久化同步确认 |
| 存储桶同步先 push 后 pull | 必须先检查协议和代际，再允许任何上传或转发 |
| `Change` 没有代际、设备实例和来源连续序号 | 旧数据无法可靠隔离，需要协议升级 |
| `.mhpack` 支持旧 oplog 合并及身份恢复 | 备份恢复也必须经过代际检查，不能绕过正常同步 |

## 4 首版架构决定

采用“**指定一个回收协调节点，普通数据仍按现有模式同步**”。建议由持有完整数据的桌面端或服务端承担；手机、部分副本不能担任协调节点。

协调节点负责成员登记、同步资格续期、可信观察时间、回收屏障和代际提交。其状态用持久化事务日志记录，并由固定协调身份认证。进程必须独占其本地状态目录。它离线时不执行回收、不办理新代际切换；现有有效资格内的普通编辑与同步可以继续。过期设备的重新登记等待协调节点恢复。

首版**不自动选举接替者**。协调节点丢失时先恢复其控制日志；不能用旧备份直接接管。无法证明控制状态连续性时，导出可恢复内容并建立新工作区，而非降低代际或冒险删除。自动故障转移需要另行实现带 fencing 的强一致控制存储。

控制日志保存工作区 ID、协调身份、成员实例、已确认水位、资格截止时间、代际清单和提交记录。它不能随业务 tombstone 一起清除；保留的是较小的协议元数据，不是全部删除块正文。

### 4.1 云端提交方式与 COS 限制

每个新代际使用不可变提交对象，例如 `control/generations/<N>/commit`，内容包括上一代提交哈希、快照哈希、覆盖范围、成员屏障证明及历史截止点。使用真正的原子“不存在才创建”；同一编号只能有一个提交。`HEAD` 后普通 `PUT` 不能代替原子操作。可变 head 仅作发现提示，客户端验证提交链并持久化已见最高代际，禁止降级。

当前适配器已经区分标准 S3 和 COS：COS 不支持该适配器需要的原子 `If-Match` 更新；条件创建只在可验证的从未开启版本控制的桶上启用。腾讯官方也说明 `x-cos-forbid-overwrite` 在启用版本控制时失效。[腾讯 COS PUT Object 文档](https://intl.cloud.tencent.com/document/product/436/7749?lang=en)

因此首版不把 COS 当作通用 CAS 数据库。协调节点串行决定控制状态，原子条件创建只用来防止代际提交被覆盖。实施前必须验证实际桶能力、权限、对象可见性，以及控制路径写入隔离；版本控制配置需在提交期间保持稳定。无法满足时关闭永久回收，使用可靠的事务控制服务后再开启。现有普通快照仍可继续工作。

共享桶密钥意味着旧客户端仍可能写入旧路径。新协议必须使用隔离的 v2 命名空间，拒绝旧代际输入；旧客户端不能发布新协议认可的提交。若要求旧客户端连云端字节都不能改写，迁移时还需更换桶凭据或隔离访问策略；应用协议不能撤销一个仍持有底层写权限的客户端。首版安全目标是防止正常旧客户端与备份造成数据复活，不承诺抵抗持有管理员密钥的恶意写入者。

### 4.2 新协议的最小信息

| 字段或记录 | 用途 |
| --- | --- |
| `workspaceId`、`protocolVersion`、`epoch` | 隔离工作区、协议和回收代际 |
| `incarnationId` | 标识设备本次登记实例；重新接入换新实例 |
| `originSeq` | 每实例持久化单调递增的来源序号，用于证明连续覆盖 |
| `checkpointId` 与哈希 | 证明安装的是哪个完整、已提交基线 |
| `leaseReceipt` | 协调节点确认的同步覆盖与资格期限 |
| `sealAck` | 屏障确认：本实例旧代际日志已封口到哪个序号 |
| `creationIdentity` | 区分新对象创建与对现有对象修改，防止把旧更新解释为新建 |

来源序号不同于当前数据库本地 `crdt_changes.seq`；后者只用于该数据库的传输游标。快照覆盖用连续来源区间或明确的分段哈希集合证明，不能以最大 HLC、最大本地 seq 代替。

资格续期必须确认：客户端已经持久化安装其声明范围的检查点、补齐所需增量，且本地待提交操作已被协调节点持久化接收。部分副本只能声明自身范围，不能证明整个工作区完整；它仍必须登记所有能产生写入的实例，并参与封口。协调节点必须收齐全部业务数据和合法来源日志。

所有入口统一检查：S3、HTTP peer、Web 副本、移动端、转发、导入和备份恢复。协议不支持则返回“需要升级”；旧代际或超期实例返回“需要重建”，在 ingest 之前拒绝。改变包外层 epoch 不能让旧操作合法，内层来源身份、序号和创建信息也必须验证。

## 5 删除资格与回收流程

### 5.1 候选规则

一个块必须同时满足以下条件：

1. 当前物化状态仍为删除，所属文档与引用关系已核对。
2. 协调节点已持续确认该删除状态至少 90 天。
3. 删除后任何新到达的有效块写入重新触发审查；保守做法是重置候选观察期。恢复后的块立即退出候选集。
4. 最近 90 天历史及窗口起点基线不依赖其待清除数据，或依赖已经进入有校验的独立历史存储；不能只删除 UI 看不见的字段。
5. 数据已被新检查点覆盖，全部未过期写入实例满足封口要求；过期实例已排除且被协议阻断。
6. 新代际提交完成、保护期已过、校验成功，才允许物理删除。

年龄使用协调节点持久化的首次观察时间和时钟健康检查。用户设备的 HLC、对象 Last-Modified、应用最后打开时间不直接授权清除。检测到系统时间跳变、回退或无法验证经过时间时暂停计时与回收。

迁移前的旧数据没有可信观察记录：**默认从协议迁移时起重新观察 90 天**，不按现在的 HLC 直接删掉 4,858 个块。本次数字用于评估潜在收益；不是上线当天的删除清单。若未来需要加速首次回收，应单独设计经过审核的迁移凭据，首版不开放这个捷径。

### 5.2 状态机

```mermaid
flowchart LR
  A[统计候选] --> B[等待成员可封口或资格过期]
  B --> C[短暂封口旧代际]
  C --> D[构建并验证新检查点]
  D --> E[原子提交新代际]
  E --> F[保留旧数据至少7天]
  F --> G[再次核验并物理清除]
```

1. 每天做一次轻量 dry-run；实际代际回收首版最多每周一次，没有候选不切换。首次必须人工审阅 dry-run 报告，之后可以按已批准策略运行。
2. 准备阶段不冻结正常编辑。尚有未过期的离线实例没有封口确认时，延期回收，不能把它提前踢出。90 天内仍保持兼容承诺。
3. 成员就绪后进入短暂屏障：冻结成员登记与资格变更；每个有效实例把旧代际操作上传并持久化封口，报告最终 `originSeq`。封口后的编辑写入独立本地待恢复队列，不能继续生成旧代际同步操作。协调节点逐一补齐至最终序号。
4. 屏障暂定 60 秒执行预算，超时取消本轮并保留候选。取消也记录持久化状态，由客户端确认后解封。不能让在线设备等待一个离线设备 90 天。
5. 从封口后的完整状态建立新代际检查点、历史边界和存活对象目录。先上传全部不可变对象，校验哈希与引用，再提交唯一代际清单。提交前绝不删除旧对象。
6. 在线客户端安装新检查点或经过等价校验的本地迁移结果，再恢复封口期间的编辑；所有游标绑定新检查点，不沿用旧数据库的序号。客户端持久化屏障状态后即使崩溃，重启也不能重新上传旧代际。
7. 提交后至少 7 天保留受管理的旧检查点、日志与所需附件，标记为恢复专用并排除出正常同步。完成新基线重放、状态哈希和来源覆盖校验后才删除。

代际提交后不能回滚成旧 epoch。发现故障时停止后续清除；从保护副本取回数据，作为经过校验的更高代际修复。这样已升级客户端不会重新接受过期操作。

## 6 超期设备如何回来

设备离线 120 天后打开，第一步只读查询当前控制状态，**不能按现有顺序先 push**。如果离线，用户仍可以查看和编辑本地内容，界面显示尚未同步。

联网重建流程：

1. 暂停旧实例的上传、转发和 ingest，先让编辑器输入落盘。
2. 制作加密本地恢复包：原数据库一致性副本、本地草稿、待提交操作、可获得的共同基线、当前可见正文与字段、未上传附件字节及清单。缺乏可靠待提交清单时，宁可保存完整本地状态，再比较差异。
3. 校验恢复包可读、内容哈希与附件完整性；空间不足或保存失败则停止重建，保留原数据库可用。
4. 在新数据库中下载并校验当前检查点和增量；旧数据库在完成交换与恢复验证前保留。磁盘空间按旧副本、恢复包、新库及附件共同计算，不假设只有一个快照的大小。
5. 为设备登记新的实例，重置与基线绑定的游标。旧操作只用来理解用户意图，不能直接传给新库的 CRDT ingest。
6. 根据下面的规则重建新的用户编辑，使用新事务、来源序号和时间戳；提交可重试，并以恢复事项 ID 去重。

| 本地改动情况 | 恢复方式 |
| --- | --- |
| 对象仍存在，存在共同基线，改动不冲突 | 三方比较后生成新的字段或块编辑 |
| 云端也修改同一内容 | 保留两份内容，展示差异，让用户决定；不按新时间戳静默覆盖 |
| 原文档仍存在，但被编辑的旧块已回收 | 重新定位插入意图；不能可靠定位时保存为恢复副本 |
| 原文档已永久删除 | 新建独立恢复文档与新 ID，不恢复旧删除 ID |
| 本地新建但从未上传 | 作为新创建提交，重映射内部引用，使用恢复事项 ID 防止重复 |
| 本地删除、移动或关系修改的目标已改变 | 不自动施加破坏性操作，交给恢复界面确认 |
| 没有共同基线 | 保存独立恢复副本，禁止猜测三方合并结果 |
| 附件未上传 | 先保全字节，再上传和恢复引用；缺失附件显示明确状态 |

任何恢复失败都不能变成“已同步”。用户可继续查看待恢复内容并导出。恢复包只有在全部事项确认后才提供删除操作，不自动到期。

正常连接文案：“此设备离线时间较长，正在保存本地编辑并更新数据。”完成后显示“数据已更新，恢复了 N 项编辑”；有冲突则显示“M 项编辑需要确认”。设置页展示最后一次完整同步、待上传数量、待恢复数量及历史可用起点；不向普通用户展示 epoch、HLC 等协议术语。

## 7 历史 备份 附件与物理清除

同步快照是当前状态基线，不能替代历史存储。现有 `documentAtVersion` 从 oplog 重建历史；回收需先保留窗口起点状态及其后完整已接收变化，记录实际覆盖范围，再删除旧数据。新设备默认只下载当前状态，历史按需获取；没有收集到的历史必须显示不可用。

历史 UI 改为“可用历史从某时刻开始”，移除“任何版本永久可找回”的承诺。对已最终回收的实体，历史恢复创建新 ID。显式归档可以保留更久，但必须显示其容量，并从回收收益中扣除；不能一边承诺彻底删除，一边把同样内容无限保存到隐藏归档。

旧 `.mhpack` 不可直接合并旧 oplog。先检查工作区和代际，跨代际作为内容恢复导入；整库恢复到原工作区同样需要新实例与重建流程。将旧备份当作新独立工作区使用时，必须隔离工作区 ID 和云端路径，禁止带旧身份、旧游标重新连回原工作区。

附件回收使用标记与清除，根集合至少包括：当前有效文档与站点文件、保留历史、7 天保护副本、正在上传的事务与已登记恢复内容。只有全部受管理引用消失且经过保护期才可清除。长期离线设备未上报的引用无法全局得知；它重新接入时只能恢复仍持有的附件字节，不能承诺找回已回收且本地没有的附件。

物理清除需覆盖：物化 `doc_blocks` 行、对应 oplog、旧同步快照、旧 segment、历史缓存、搜索索引缓存，以及不再被引用的附件。云端版本控制、对象锁、备份策略可能保留历史版本，需要单列实际释放量。SQLite 删除行、页复用与 VACUUM 后归还文件空间分别报告；移动端只在空闲且空间足够时压缩文件。

## 8 从源头减少删除块

先实现明确的块编辑接口，编辑器保存稳定 block ID 和读取版本。普通文本修改更新同一块的 `text`；移动只更新顺序；拆分、合并各定义保留哪个身份。真正删除才生成 tombstone。已有全文接口仍兼容，但需有确定的映射规则与版本保护。

不能简单按数组位置把不同段落当成同一块。重复段落、粘贴、撤销、Markdown 往返、段落移动、输入法组合输入都要覆盖。全文提交时应携带基线版本；基线已经过时需重算或报告冲突，避免旧编辑器内容覆盖远端新内容。

当前是字段级 LWW，不是字符级协同编辑。稳定块 ID 会让并发修改更容易落到同一 `text` 寄存器；必须保留冲突副本或阻止无提示覆盖，不能把 ID 优化描述成已经解决文本协作。首版不引入新的字符 CRDT。

验收目标：同一段落连续修改 100 次，保留 1 个有效块，普通修改不新增删除块；仍可产生文本历史，但历史由保留窗口压缩，不再扩大当前状态快照中的实体数。

## 9 实施顺序和交付边界

| 阶段 | 交付 | 开启永久回收 |
| --- | --- | --- |
| A | 正式构建验证 iOS 解析修复；加入快照体积、字段数、解析耗时与删除块年龄统计 | 否 |
| B | 稳定块身份、版本保护、冲突保全；增加纯只读回收 dry-run | 否 |
| C | 新协议、来源连续序号、成员资格、单协调节点、代际清单、所有入口隔离 | 否 |
| D | 恢复包、重建、冲突界面、历史覆盖、备份导入与附件引用保护 | 否 |
| E | 迁移到 v2 路径，验证基线与真实 COS 条件写入能力，开始 90 天观察 | 否 |
| F | 通过验收后审阅首次回收报告，提交新代际，至少 7 天后清除 | 是 |

迁移要显式登记要保留同步资格的设备，不能将所有历史作者节点自动当成活跃成员。已知但尚未升级的设备在迁移兼容期内保留数据保护；切换后它们不能写入 v2，升级后通过恢复流程接入。只要还有未设防的旧入口能写入新状态，F 阶段不得启用。

主要改动面：`documents.ts`、`blocks.ts` 与各端编辑器；`crdt.ts`、`sync/protocol.ts`、`sync/storage.ts`、`sync/client.ts` 与接收入口；新增协调控制日志、成员资格和回收状态机；`compact.ts`、`history.ts`、`snapshot.ts`、附件 GC；本地 drafts 与客户端 session lifecycle。现有快照发布者选举可继续用于普通非破坏性快照，不与回收协调权混用。

## 10 必须通过的验收

| 场景 | 必须成立的结果 |
| --- | --- |
| 设备离线 89 天，持有未上传修改 | 资格有效时不能被提前排除；回收等待封口或自然过期 |
| 设备超过 90 天未确认同步 | 上传前进入重建；本地编辑先保全；不受 HLC 新旧影响 |
| 超期设备没有本地修改 | 完整重建后状态与当前检查点一致，无已删内容复活 |
| 超期设备有修改、附件和未保存编辑器输入 | 重建前落盘并校验；失败不清空旧库 |
| 对已回收文档继续编辑 | 恢复为新 ID，原删除实体不复活 |
| 来源最大 HLC 很新但中间缺 segment | 不视为完整确认，不提交回收 |
| 屏障期间继续编辑、实例崩溃重启 | 新编辑被保全；已封口实例不再写旧代际 |
| 提交前后各步骤断电、超时或网络重试 | 未提交不删；提交后只向前恢复；恢复事项不重复 |
| 两个错误启动的协调进程竞争提交 | 同一代际至多一个有效提交；失败者不得执行清除 |
| COS 条件能力不明、权限不足、版本控制变化 | 永久回收关闭，不降级为非原子覆盖 |
| 旧 peer、旧桶快照、旧备份重新出现 | 所有入口拒绝旧操作流，不能经第三台设备转发洗成新操作 |
| 部分副本确认或设备仅心跳 | 不虚报全局覆盖、不续期不合格资格 |
| 时钟大幅快进或回退 | 不提前到期、不提前删除 |
| 保留窗口内历史、窗口基线和附件 | 回收前后可重建内容一致，缺失覆盖可识别 |
| 新代际当前状态 | 所有有效文档、字段、顺序与引用语义一致；只移除批准候选 |
| 同一段落编辑 100 次与双端并发编辑 | 块 ID 稳定，冲突不静默丢失 |

用 `bun test` 运行模型与故障注入测试；先用临时数据库和隔离桶验证，不用用户真实桶做删除实验。iOS 与 Android 都需要实际验证大快照、低空间、后台暂停、杀进程恢复及输入法状态；不能仅凭桌面测试宣布完成。

## 11 运行指标与调整依据

报告当前块数、删除块数、年龄分布、实际可回收数、被历史或设备阻挡数量、旧快照与日志字节、历史与保护副本字节、实际释放空间、同步总耗时、解析与 ingest 耗时、重建次数、恢复冲突数。日志只含聚合数与必要协议标识，禁止正文和凭据。

先运行 90 天策略，再用真实的“最后合格同步间隔分布”和恢复结果评估是否调整。若空间增长仍快，优先检查稳定 ID 是否生效、是否反复全文重建及是否存在未退出的屏障；不自动缩短保留期。当前数据支持采用 90 天作为保守默认，不支持精确预测节省字节或旧设备受影响比例。
